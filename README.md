# Учимся запускать сервис: Node.js → Docker → GitHub Actions

Исходный код — TypeScript, сервер — встроенный `node:http`, рабочие npm-зависимости отсутствуют. TypeScript, Jest и Prettier устанавливаются в собственный `node_modules`. Выполняйте все команды из этой папки, используя npm, а не корневой pnpm.

## 1. Запуск без Docker

Нужен Node.js 24 с npm. Если используете nvm, выполните `nvm install` и `nvm use` в папке проекта.

```sh
node --version
npm ci
npm run build
npm start
```

`npm ci` устанавливает точные версии из `package-lock.json`. `build` компилирует `src/*.ts` в `dist/*.js`. `start` выполняет `node dist/server.js`. Терминал остаётся занят сервером; сообщение `Listening on 0.0.0.0:3000` означает, что он слушает подключения. Для остановки нажмите Ctrl+C.

В другом терминале выполните:

```sh
curl http://localhost:3000/
curl http://localhost:3000/health
curl -i http://localhost:3000/missing
```

Первый ответ содержит `message`, `version` и `hostname` вашей машины. Второй — `{"status":"ok"}`. Последний — HTTP 404 и `{"error":"Not found"}`. POST на эти адреса также возвращает 404.

```sh
PORT=3001 APP_MESSAGE='Hello from my laptop' npm start
```

Теперь запросы отправляйте на `http://localhost:3001`. PORT должен быть целым числом от 1 до 65535; по умолчанию используется 3000. APP_MESSAGE меняет приветствие без изменения кода. Ctrl+C и SIGTERM корректно закрывают сервер; оставшиеся соединения закрываются принудительно через 5 секунд.

## 2. Проверки

```sh
npm run typecheck
npm test
npm run format:check
```

Jest поднимает настоящие HTTP-серверы на временных портах и закрывает их после каждого теста. Покрытие HTTP-обработчика должно быть не ниже 80%; отчёт появляется в `coverage`. Входная точка процесса и учебный скрипт проверки контейнера в этот показатель не входят.

Если проверка оформления сообщает об отличиях, выполните `npm run format` и повторите её.

## 3. Подготовка Docker на macOS

Установите [Docker Desktop](https://docs.docker.com/desktop/setup/install/mac-install/) для своего процессора (Apple Silicon или Intel), откройте приложение и дождитесь запуска движка.

```sh
docker version
docker info
```

В `docker version` должны быть секции Client и Server. `command not found` означает, что CLI не установлен или не находится в PATH. Ошибка подключения к daemon означает, что движок Docker ещё не запущен. На macOS Docker Desktop запускает Linux-окружение, в котором работают наши контейнеры.

## 4. Собираем образ

Сначала остановите локальный сервер, чтобы освободить порт 3000.

```sh
docker build -t my-project:local .
```

Точка задаёт контекст сборки: только текущую папку. Docker читает `Dockerfile` и создаёт образ с именем `my-project:local`.

Образ — подготовленные файлы приложения и окружение. Контейнер — запущенный экземпляр образа. Из одного образа можно запустить несколько контейнеров.

Dockerfile состоит из двух этапов:

1. `build`: берёт Node.js 24, устанавливает зависимости через `npm ci` и компилирует TypeScript.
2. `runtime`: берёт Node.js 24 и копирует только `dist`. Компилятор, Jest и локальные зависимости в этот этап не попадают. Приложение запускается пользователем `node`.

Основные инструкции:

| Инструкция                       | Когда и что делает                                             |
| -------------------------------- | -------------------------------------------------------------- |
| `FROM`                           | Выбирает базовый образ для этапа                               |
| `WORKDIR /app`                   | Задаёт рабочую папку внутри образа                             |
| `COPY`                           | Копирует файлы в образ                                         |
| `RUN npm run build`              | Выполняется во время сборки образа                             |
| `ENV PORT=3000`                  | Задаёт значение переменной окружения по умолчанию              |
| `EXPOSE 3000`                    | Документирует внутренний порт; не открывает его на компьютере  |
| `CMD ["node", "dist/server.js"]` | Задаёт команду, которую Docker выполнит при запуске контейнера |

`.dockerignore` исключает локальные `node_modules`, `dist`, Git и env-файлы. Поэтому сборка не зависит от предварительного `npm run build` на компьютере. Для первой сборки нужен интернет: Docker скачивает базовый образ и npm-пакеты.

## 5. Запускаем контейнер

```sh
docker run --rm -p 127.0.0.1:3000:3000 --name my-project my-project:local
```

Docker создаёт контейнер, выполняет CMD, Node.js загружает сервер, сервер начинает слушать `0.0.0.0:3000` внутри контейнера.

- `--name my-project` задаёт имя контейнера.
- `--rm` удаляет контейнер после остановки; образ остаётся.
- `-p 127.0.0.1:3000:3000` соединяет порт 3000 компьютера с портом 3000 контейнера и разрешает доступ только с этого компьютера.
- `0.0.0.0` в приложении позволяет принимать подключения через сеть контейнера.

В другом терминале:

```sh
curl http://localhost:3000/
docker ps
docker logs my-project
node scripts/check-http.ts
docker stop my-project
```

`hostname` в ответе теперь соответствует контейнеру. `docker ps` показывает работающие контейнеры, `logs` — вывод процесса, `stop` отправляет сигнал остановки. HTTP-проверка ждёт готовности до 30 секунд, затем проверяет ответ `/`.

Запустите тот же образ с другим приветствием:

```sh
docker run --rm -p 127.0.0.1:3000:3000 --name my-project -e APP_MESSAGE='Hello from Docker' my-project:local
```

Проверьте через `curl`; для автоматической проверки передайте то же ожидание: `APP_MESSAGE='Hello from Docker' node scripts/check-http.ts`.

## 6. Меняем код и наблюдаем пересборку

Остановите контейнер. В `src/app.ts` поменяйте стандартное приветствие. Запустите старый образ снова: ответ останется прежним, потому что исходники не примонтированы к контейнеру, а скопированы при сборке.

Остановите старый контейнер и выполните:

```sh
docker build -t my-project:local .
docker run --rm -p 127.0.0.1:3000:3000 --name my-project my-project:local
```

Теперь ответ изменится. Пересборка образа сама по себе не обновляет уже запущенный контейнер — его нужно пересоздать. После упражнения верните приветствие либо обновите ожидаемые значения в тесте и `scripts/check-http.ts`.

Можно запустить второй экземпляр того же образа на другом порту компьютера: `docker run --rm -p 127.0.0.1:3001:3000 --name my-project-second my-project:local`. Внутренний порт обоих контейнеров остаётся 3000.

## 7. Переносим только учебный проект в GitHub

В GitHub создайте пустой репозиторий `my-project` без README и шаблонов. Не загружайте монорепозиторий Arcadia. Содержимое этой папки должно стать корнем нового репозитория: в частности, workflow должен лежать в `.github/workflows/ci.yml` от корня.

Следующие команды выполняйте самостоятельно в терминале. Они копируют учебный проект в отдельную папку; исходная папка не становится вложенным Git-репозиторием. Выберите ещё не существующий каталог назначения.

```sh
mkdir -p ~/docker-learning/my-project
rsync -av --exclude=node_modules --exclude=dist --exclude=coverage --exclude=.git --exclude='.env*' --exclude=.npm-cache --exclude=.DS_Store /Users/dchertenko/arcadia/games/frontend/services/my-project/ ~/docker-learning/my-project/
cd ~/docker-learning/my-project
git init -b main
git add .
git commit -m "Add Docker learning service"
git remote add origin https://github.com/YOUR_USERNAME/my-project.git
git push -u origin main
```

Замените YOUR_USERNAME своим именем. GitHub запросит настроенную авторизацию Git. Секреты приложения и доступ к серверу для этого упражнения не нужны.

## 8. Смотрим GitHub Actions

После push откройте вкладку Actions. Workflow запускается на push, pull request и вручную через Run workflow. GitHub выделяет временную Ubuntu-машину — runner — и последовательно выполняет:

```text
Checkout кода
  → Node.js 24
  → npm ci
  → форматирование, типы, Jest
  → компиляция TypeScript
  → docker build
  → docker run
  → HTTP-проверка через опубликованный порт
  → удаление контейнера
```

Раскрывайте каждый шаг и сопоставляйте команды со своими локальными запусками. При ошибке workflow показывает логи контейнера, если он был создан, и пытается удалить его при любом исходе.

Это CI: автоматическая проверка работоспособности. Образ не отправляется в registry, контейнер не становится публичным стендом и не продолжает работать после job. `localhost:3000` в этом запуске относится к runner GitHub, а не к вашему компьютеру.

## 9. Создаём PR и намеренно ломаем проверку

В отдельной копии GitHub-проекта:

```sh
git switch -c learn/failing-test
```

В `tests/app.test.ts` замените ожидаемое стандартное приветствие на `Wrong greeting`, оставив код сервиса прежним. Затем:

```sh
git add tests/app.test.ts
git commit -m "Demonstrate a failing CI test"
git push -u origin learn/failing-test
```

Создайте PR через GitHub. Откройте Checks → упавший job → Test HTTP service. Jest покажет разницу между ожидаемым и полученным ответом. Сборка контейнера после этой ошибки не выполняется. При push в ветку с открытым PR могут появиться два запуска: для push и pull_request.

Верните правильное ожидание, сделайте новый commit и push. Новая проверка должна пройти. Так можно увидеть, как CI проверяет каждую новую версию кода.
